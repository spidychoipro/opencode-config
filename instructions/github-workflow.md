# GitHub 작업 흐름 규칙 — 필수

사용자가 관리하는 저장소에서 버그/불편과 기능 추가를 아래 방식으로 처리한다.

## 1. 버그 / 불편 → 이슈를 열고 고친다

대상: 사용자가 "이건 아니야", "이게 불편해"라고 제보한 것. 그리고 사용자가 "스스로 버그를 찾아 고쳐"라고 지시해서 네가 발견한 버그도 **똑같이** 여기에 해당한다.

1. **GitHub 이슈를 먼저 연다.** (코드 수정보다 이슈 먼저)
2. 이슈 본문은 **한국어**로 쓴다. 증상 / 재현 절차 / 원인 / 기대하는 동작 / 환경 를 담되, 문서는 3번 규칙(사람 톤)을 지킨다. 묶음 제목이나 템플릿 문구로 채우지 말고 문단으로 쓴다.
3. 원인을 파고드는 동안 진행 상황을 **이슈 댓글로** 남긴다.
4. 수정은 `fix/issue-<번호>` 브랜치에 커밋하고 **PR**을 연다. PR 본문에 `Closes #<번호>` 를 넣어 이슈와 연결한다.

## 2. 기능 추가 → PR로 올린다

대상: "이 기능 추가해줘" 처럼 요구가 완성되어 넘어온 경우. 이슈는 열지 않는다.

- `feat/<짧은-요약>` 브랜치에 커밋하고 **PR**을 올린다.

## 3. 이슈를 고칠 때 댓글은 반드시 남긴다

- 이슈를 열었으면 **사람이 대화하듯이 댓글로** 남긴다. (원인 확인 → 수정 완료 → PR 링크)
- 커밋만 하고 이슈 댓글을 남기지 않는 것을 금지한다. 마지막에 이슈가 정리된 상태로 마무리할 것.
- **고치기가 끝나면 이슈를 바로 닫는다.** (`gh issue close <번호> --comment "..."`) PR만 열어놓고 이슈를 열어두는 상태로 끝내지 않는다. 닫을 때도 사람 톤으로 한 줄 남긴다.
- 이슈 본문 / 댓글 / 커밋 메시지 / PR 본문은 저장소 주 언어를 따른다. (이 저장소는 한국어)

### 댓글은 AI처럼 쓰지 않는다 (강력)

이슈 본문·댓글·PR 본문은 **실제 사람이 쓴 것처럼** 써라. AI 티가 나면 신뢰를 잃는다.

- 짧게. 3~5문단 이내. 서론/결론/요약으로 감싸지 말고 바로 내용.
- 번호 매긴 목록, `---` 구분선, `**강조**`, 표 같은 정돈된 포맷 남발 금지. 필요하면 그냥 문단.
- 존댓말·높임 말투 쓰지 말 것. `~습니다` `~이네요` `~해 주세요` `고쳐보겠습니다` 다 금지.
  반말 + `~음` `~함` `~더라` `~거든` 같은 구어체로 끝낸다.
- "분석결과", "원인을 파악했습니다", "기대하는 동작", "다시 한번 확인해 주세요",
  "도와드리겠습니다", "감사합니다" 같은 템플릿·상투 표현 금지.
- 한 문단에 사실 2~3개씩 흘려보내도 된다. 또박또박 설명하려고 effort 쓰지 말 것.
- 좋은 예: `뭐 누가 한글 버전으로 ai글을 사람 처럼 바꾸는걸 github에 올렸다는데 설치하고 싶으면 설치하던가`
- 나열이 필요하면 짧게 `- ` 로. 문단으로 흐르는 게 더 자연스러우면 문단으로.
- 이모지 남발 금지. 사용자가 썼을 때만.

## 4. 도구

`gh issue create`, `gh issue comment`, `gh issue close`, `gh pr create`, `gh pr comment` 를 사용한다.
PR은 저장소 과거 이력이 `main` 직접 커밋이더라도 **브랜치 + PR**을 기본으로 한다.
